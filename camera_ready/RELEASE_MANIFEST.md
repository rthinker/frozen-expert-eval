# Release manifest: paper results, steps, outputs and tolerances

Builder v18 (`camera_ready/scripts/authoring/generate_camera_ready_tables_v18.py`) rebuilds 25 DF40 tables and three additional tables (power thresholds, head-setting sensitivity, and protocol examples). Table identifiers follow the paper.

The stored `camera_ready/provenance/05_number_provenance.csv` contains 1,937 public quantities: 901 table entries (857 associated with the printed tables and 44 with the three additional tables), 114 text entries, 7 audit entries and 915 check-table entries. Source paths, hashes and explanatory notes identify the public artifacts. `camera_ready/provenance/paper_table_locations.json` maps stable quantity ids to current table numbering and additional analyses. C24 compares every rebuilt quantity with this public ledger. Completion requires all 52 products: 25 paper tables,
three additional tables, 21 check tables, the ledger, the posted-number report and the location map.
The report must contain exactly the 96 expected unique quantity IDs, and the current table sets and map must match.

The four `T1.<pool>.logo.delta_n500` identifiers now map to Appendix F, alongside `appF.small_sets.*`. C24 writes current tables to `output/tables/tables/paper/`, the three former tables to `output/tables/tables/additional/`, and a new location map. `provenance/APPENDIX_ADDITIONAL_DETAILS.md` documents the power calculation and secondary pool analyses. This manifest maps current paper items and retained additional analyses to harness steps, outputs and checks.

Block A contains the submitted results. Block B contains LOGO reruns, and Block C contains
additional analyses. Paired sign tests exclude exact ties.

The exact commands below are **harness-owned commands**: their destinations include supplied results.
Run a step with `python camera_ready/scripts/review/reproduce_all_v4.py --only <step>` so its outputs are
backed up first. When calling a script directly, give it a separate scratch `--out` or `--out-dir`.
For example, C01's standalone report can use `--out camera_ready/output/checks/split_reuse.json`.

C24 reads preserved reference inputs from `camera_ready/inputs/`. The archived configuration is part of that snapshot. Use `configs/` for the current runner configuration. The 49 ledger rows that name `configs/experts.yaml` hash that archived copy, `camera_ready/inputs/experts.yaml` (`2d71b9fe6523228b`), not the current `configs/experts.yaml` (`803469b1efb2c5ca`). The two files differ only in their comments and parse to the same configuration.

C24 uses the three matched arch6 reference files in `camera_ready/inputs/` for the posted-number check:
`11_disjoint_arch6_d256.json`, `A3c_logo_extended_rungs_arch6.json`, and
`A3c_logo_combined_ceiling_arch6.json`. A fresh Block A result does not replace one member of that paired set.
The harness stages other inputs regenerated by the selected run.

## Steps of blocks B and C

Block A runs the reviewed commands (`python camera_ready/scripts/review/reproduce_all_v4.py --dry-run --blocks A`).
`[--gpu-name <name>]` and `[--resume]` are added by the harness where they apply; `<DF40 lists>` is the folder
given with `--df40-json`. C08 also preserves the pre-exclusion `logo_arch6` branch
in `full_ladder_stats.json` (ceiling 0.818, FS1 margin +0.080). Current content-excluded LOGO results
(ceiling 0.817, margin +0.081) are in `mitigation/mitigation_stats.json`, as used by the paper.
The paired sign tests exclude exact zero differences; an all-tie vector has p=1.

The statistics of steps B31, B32 and C08a (`full_ladder_stats_v13.py`) stop when a LOGO run,
its richer-input run, one of the eight held-out generators or a mechanism run is missing, or when the full ladder
(the ten base methods and the twelve richer-input candidates) is not complete in an analysed fold, unless a partial
analysis is asked for by name (`--allow-ten-methods`, `--allow-partial-folds`, `--allow-incomplete-ladder`; the
result then records what it lacks under `input_completeness`); the harness never asks for one. They also stop,
whatever the options, when runs analysed together do not belong together (the next paragraph). Their `mitigation_numbers.md` lists selected quantities from the LOGO statistics. `tests/test_full_ladder_stats_v13.py` checks that the report matches the rendering of the supplied statistics. C24 performs the separate ledger comparison. Use `provenance/paper_table_locations.json` for current table numbering. Step B31's self-test compares with the stored standard-split statistics in
`camera_ready/inputs/`, which no step rewrites. Step C01 runs version 3 of the reuse check: routes carried over from
the stored result are not compared with the expected counts, and with `--df40-raw` any cached row without its image
file stops the check and blocks C24. Standalone write protections apply to the camera-ready scripts described here.
The root `scripts/04_*` through `scripts/17_*` and `camera_ready/scripts/authoring/full_ladder_stats_v4.py` can
overwrite files in release output directories when invoked directly. The analyses stop before any work unless `CR_RESULTS_DIR` names another folder, the runners and gates
refuse such an output path, the expert-side check (C04, version 3) and the Appendix H comparison (C13, version 2)
write only where `--out` says, and the statistics (B31, B32, C08a, version 13), the standard-split statistics (C08,
version 3) and the Appendix H table (C12, version 3) refuse to write among the stored results. The harness marks the steps it runs with the environment variable `REPRO_ATTEMPT_ID`.

Runs analysed together must belong together (`camera_ready/scripts/runs/ladder_checks.py`, used by the statistics,
the combined ceiling of steps B10, B22, B24 and B26, the sensitivity summary and the table builder): the same pool,
exclusion and per-fold row counts (test, FIT, SELECT, excluded training rows) and, when both runs record them, the
same membership fingerprints of FIT and SELECT. The current runners (LOGO v4, richer inputs v3, width controls v5)
record the fingerprints, and reuse only checkpoints that hold them. The stored runs record none, so two of them are
accepted together only when both are listed in one group of `camera_ready/provenance/trusted_run_pairs.json`
(groups of runs produced together from the same folds, by content digest; `scripts/review/trusted_run_pairs_v1.py
--check` compares it with the stored files); matching fold names are never enough. A rerun of one run of a pair
therefore needs the other rerun too. `TIMINGS.md` says whether a run was complete or partial, lists the steps not
run, skipped or not finished (their stored outputs were kept), names what no run of the harness covers, and compares
a time the paper states only with a run that covers it.
The checks that report a verdict (C10, C14 to C16, C22) exit with status 1 when it is negative,
the LOGO and width-control runners take each held-out generator once in `--folds` and write nothing in a dry run, and
a resume of C20 reuses only the caches written for the same manifest, inner assignment, construction and device.

## Tolerances

Rules for comparing a rerun with the pinned library versions against the supplied values. These are comparison thresholds, not measured reproduction results:

* every compared value: finite (NaN or infinity fails unless the reference holds the same value) and valid for its
  kind: p-values, and AUROCs and other probabilities whose reference lies in [0, 1], within [0, 1]; counts (wins,
  folds, samples, seeds, epochs) non-negative integers; wins at most their number of folds; an early-stopping epoch
  at most the epochs run;
* every status a result records (gate verdicts, `gate_G4_status`, the audit's identity checks): PASS, report or
  COMPLETE;
* deterministic methods (logistic regression, XGBoost with fixed seeds, PCA with a fixed seed, counts,
  manifests): within 1e-4 (1e-3 for the three-class heads on fixed outputs and the strict-refit checks), as
  the reviewed harness; the L-BFGS fits can move more between platforms (see [reproduction limitations](REPRODUCTION.md#reproduction-limitations));
* Block A files marked stochastic in the reference: within 0.005, reported as WARN up to 0.1 and failing beyond.
  Valid changes above 0.1 in the reviewed LOGO report's win counts and paired p-values are reported as ENV.
  The prediction-space results in `04_ds_*.json` use the 1e-4 tolerance for the entire file, including PS3,
  PSD, PSE and PSF (the MLP heads);
* FS2, the statistics derived from it (the `fs_*` values of the LOGO runs, the FS2 values of the standard-split
  statistics) and the three-class heads trained on a GPU (FS2-K3, PS3-K3): within 0.005, reported as ENV when they
  differ more, since they depend on the GPU and software environment (Appendix J.9), and failing beyond 0.1 (three
  times the largest change recorded between environments: 0.033, FS2 on the 101-sample HeyGen fold of clip4).
  Values that move in steps when one fold or seed changes (fold counts, rank-test p-values, per-seed values,
  early-stopping epochs) need only be finite and valid; the configuration recorded with them (seeds, layer sizes, learning
  rate, fold and seed counts) must equal the reference. The stored three-class run
  of Table A18 used an RTX 2070 Super; on an RTX 5080 the FS2-K3 head trains slightly differently (two of its
  24 seed-fold fits stop one epoch earlier) and gives 0.944 for the printed 0.945 (FS2-K3 minus the PS head
  selected on SELECT: -0.010 for -0.009);
* skip markers: no step of blocks B and C writes one, so a result file that is a skip marker fails; in Block A only
  the two documented full21 memory-budget results (`04_ds_full21_rawfeat.json`, `06_bootstrap_full21.json`) may be
  skip markers;
* Block A: the comparison uses only fields the rerun scripts write. The reference omits the PSB AUROC on
  DeepFaceLab for arch6, mixed6 and low_het4 because the supplied per-run and aggregate values disagree.
  The remaining reference values and the checks above still apply;
* the rebuilt number ledger: every number finite, p-values and counts within their range, and a value read from a
  result valid for its key; then compared with the stored ledger at the printed precision, numbers that depend on
  the GPU (by their source key) reported as ENV and timings as machine-dependent;
* the reuse check (`split_reuse_check.json`): a stored copy must hold every value of its reference; one rewritten
  by a run must hold every count from the feature cache, plus route A when the run was given DF40's lists and the
  image-file checks when it was given the image root, whatever the file itself declares; the routes a run does not
  compute are carried over from the stored result;
* digests (three-class manifests and inner assignments) and gate verdicts: exact; a gate file the run did not
  rewrite is also compared value by value, and a stored file whose rows are excluded from the comparison (the
  three-class fold manifest) must be the reference's source, byte for byte with CRLF or LF line endings;
* the retained additional power simulation (seeded): powers within 1e-3, as fractions of the simulated sets; the
  three detection thresholds exact;
* timing fields: recorded in the run log and `TIMINGS.md`, never compared.

## DF40's split lists

Steps C01 (route A of the reuse counts, from the lists as published), C04 and C14 to C16 (from the folder C00 writes) read DF40's own split lists. Step C00 (`scripts/analyses/prepare_df40_lists_v2.py`) first rewrites the public files into the path form of the cache's sample ids (`DF40_train/<method>/frames/...` becomes `<method>/ff/frames/...`, `deepfakes_detection_datasets/FaceForensics++/...` becomes `FaceForensics++/...`). With the rewritten public lists the stored three-class folds, exposure audit and frozen manifests are reproduced exactly (content and digests; the files' line endings follow the platform), the inner assignment digests of Table A18 are equal, and every overlap count of the expert-side check is equal; its count of unique training paths (703,223 in the authors' local copy, which omits e4e's 29,126 images, and 732,349 in the public `DF40_all.json`) is reported as ENV, and any other value fails. The reuse and expert-side checks include GIF paths (247 MidJourney test images). A resume reruns the steps whose DF40 inputs changed at the same paths: DF40's lists are part of the fingerprints of C00 and C01, and with `--df40-raw` C01's fingerprint also holds the existence and size of every image file it looks up (the only things it reads from the image root); every later step that reads their outputs reruns with them. Steps C04 and C14 to C16 accept only a folder written by C00 (it holds `PREPARED.json`). `--df40-raw` names an image root in which `<root>/<sample id>` is each cached image, as in the DF40 folder the cache was extracted from (the ids are in `camera_ready/output/ids/`); DF40's public download is laid out differently, so with it C01 stops, writing nothing. In a full run this blocks C24 and causes a nonzero exit. `--only C01` with both options checks an image root in a few minutes.

## Interpreting the supplied results

In LOGO fold results, `fs_mlp_mean` is the AUROC of predictions averaged across the FS2 seeds.
`fs_mlp_per_seed` lists the AUROC of each seed before averaging predictions. For arch6, averaging
the former across folds gives 0.896, as reported in the paper. Averaging the individual seed AUROCs
across folds gives 0.889.

* `output/results/mitigation/SCORE_PRECISION_NOTE.md` explains the comparison of per-sample FS1 scores in gate G5.
* `output/results/sensitivity/PROVENANCE.md` describes the inputs and settings for the sensitivity analyses.
* `maintained/metrics_v2.py` provides explicit handling of single-class AUROC, average precision and
  degenerate bootstrap resamples for reuse outside the paper pipeline.
